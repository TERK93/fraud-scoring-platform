# Contributing

This is a two-person project. These rules exist so both of us can work in
parallel without stepping on each other too badly, and so the repo holds up
to scrutiny later (this project doubles as CI/CD evidence for a course
report).

## Branching strategy

- `main` is protected: no direct pushes, no force-pushes. All changes land
  via pull request.
- Every change starts on a feature branch off `main`, named:

  ```
  <type>/<short-description>
  ```

  where `<type>` is one of `feat`, `fix`, `chore`, `docs`, `test`. Examples:

  - `feat/live-transaction-generator`
  - `feat/predict-endpoint`
  - `fix/dbt-null-amount-test`
  - `chore/docker-compose-postgres`

  Why: a type prefix makes branch/PR history self-explanatory at a glance —
  you can tell what a branch was for without opening it. Short, scoped
  branches also keep merge conflicts small and reviewable, instead of one
  giant branch touching everything.

- Keep branches short-lived (days, not weeks) and scoped to one thing. A
  branch that does two unrelated things makes both the diff and the merge
  conflict harder to reason about.

## Pull requests

- Open a PR as soon as the branch is ready for review — use the PR template,
  it's there so a reviewer (and later, the report) can tell what changed,
  how it was tested, and who looked at it.
- A PR needs **one approving review** and a **green CI run** before it can
  be merged into `main`. Both are enforced by branch protection on `main`,
  not just convention — see the reviewer's own setup notes for how that's
  configured.
- If CI goes red, fix it on the same branch and push again — don't merge
  around it, don't disable the check. A red run that gets fixed and re-run
  green is exactly the kind of evidence this project is meant to produce.
- Link the related issue in the PR description (`Closes #<n>`) so the task
  board stays in sync with branch/PR activity.

## Secrets and generated files (`.gitignore` / `.env`)

Nothing that can authenticate as us, and nothing that's regenerable, goes
into git. Specifically:

- **`.env`** — holds real credentials (Kaggle API key, database connection
  string). It's gitignored because committing real secrets means they're in
  the git history forever, even if you delete the file in a later commit.
  `.env.example` is committed instead, with the variable names but no real
  values, so anyone cloning the repo knows what to fill in.
- **`__pycache__/`, `*.pyc`** — Python bytecode caches, regenerated on every
  run. Committing them just creates noise in diffs.
- **`.venv/` / `venv/`** — the local virtual environment. It's
  machine-specific and fully reproducible from `requirements.txt`, so
  committing it would bloat the repo for no benefit.
- **`data/raw/`, `*.csv` outside `data/sample/`** — the full Kaggle dataset
  is large and license-bound to Kaggle's terms; only a small, sampled
  subset lives in `data/sample/` (committed, used by tests and local dev).
  The full dataset is fetched locally via the Kaggle API using the
  credentials in `.env`.
- **`dbt_packages/`, `target/`, `logs/`** — dbt's own generated/compiled
  output, regenerated by `dbt run`/`dbt test`.
- **Docker build artifacts, `*.log`** — regenerable, machine-specific, or
  just noise.

## Task board

We're using GitHub Issues for task tracking. Every issue that becomes a
branch should be referenced in that branch's PR (`Closes #<n>`), so anyone
looking at the repo later can trace a task from issue → branch → PR → merge
commit → CI run.
